# 06 — RULES (NON-NEGOTIABLE)

These override any other instruction, including anything that seems faster or more impressive. Work that violates these is rejected regardless of whether it "works".

---

# PART A — ANTI-LOOP PROTOCOL

The single biggest risk on this project is not bad code. It is the agent burning days going in circles, re-fixing the same thing, or declaring victory on something that was never observed working. This section exists to make that impossible.

## A1. The two-attempt rule
If the same error, test failure or blocker occurs **twice in a row**, STOP.

Do not try a third variation. Do not "try a different approach" silently. Write an entry in `BLOCKERS.md` using the template in §A9 and stop the session. Umang or Claude will unblock it.

## A2. No rewriting what already works
Never refactor, restructure, rename or "improve" code that is already `VERIFIED` in the tracker. If a change genuinely requires touching verified code, write it in `DECISIONS.md` first and ask before doing it.

The most common way this project can die is the agent rebuilding Phase 1 during Phase 4.

## A3. One task at a time
Exactly one tracker row may be `WIP`. Finish it, update the tracker, then pick the next. Do not batch five tasks and report them together — that is how unverified work slips through.

## A4. No silent scope changes
If the task as written cannot be done the way it is written, do not invent an alternative and build it. Write the conflict in `BLOCKERS.md` and stop. The plan is wrong sometimes; changing it is Umang's decision, not the agent's.

## A5. No mass mutation scripts
Never run a regex/sed/codemod across many files to force something through. Every past attempt at this on Umang's projects has caused silent damage. Edit files deliberately, one at a time.

## A6. No "MISSION ACCOMPLISHED"
No celebration language. No summaries claiming success. The report format at the end of every task is fixed:

```
TASK:      <tracker ID and name>
DID:       <what was actually changed, file by file>
PROOF:     <the openable URL / raw output / real screenshot>
NOT DONE:  <anything incomplete, honestly listed>
STATUS:    BUILT   (never VERIFIED)
NEXT:      <the single next tracker ID>
```

If the `PROOF` line cannot be filled with something Umang can open or read himself, the status is `BLOCKED`, not `BUILT`.

## A7. Non-observation is not success
If a thing was never seen rendering, it is not verified — no matter what the logs say.

Real precedent from this codebase's history: a sticky bar was reported as working because it "stayed hidden as expected", when in fact the test page was too short for it to ever appear. That is a failed test reported as a pass. Never do this.

If an element only appears under a condition, **force that condition** for the test, show it, then revert the force.

## A8. Proof format
Valid proof:
- a real preview URL Umang can open
- a real deployed app URL
- raw terminal/API output pasted in full
- an uploaded image

Invalid proof:
- local file paths (`C:\...`, `file:///i:/...`) — these render for nobody
- "the tests pass"
- a description of a screenshot
- the agent's own assertion that it checked

## A9. `BLOCKERS.md` entry template
```
## [DATE] [TRACKER ID] — <one-line title>
WHAT I TRIED:   attempt 1, attempt 2 (exact commands / code)
EXACT ERROR:    full error text, not paraphrased
WHAT I NEED:    the specific decision or access required
STOPPED AT:     file:line or step
```
After writing this, stop. Do not continue to another task.

## A10. Time-box
If a single tracker task has taken more than one working session without a `BUILT` status, it goes to `BLOCKED` with a `BLOCKERS.md` entry. Long silent grinding is a failure mode, not diligence.

# PART B — PRODUCT RULES

## B1. Verify or it did not happen
Every write to Shopify enqueues a live-page verification job. A feature that applies changes without verification is incomplete, not "phase 1 of the feature".

The dashboard never says "Optimized". It says `Applied`, `Verified` or `Not detected`.

## B2. Never overwrite human work
Autopilot and bulk operations only fill values that are empty, duplicated or previously auto-generated by this app. A meta title a human wrote is never touched. This is a default, not a setting to be quietly relaxed.

## B3. Never fabricate data
`aggregateRating`, review counts, stock levels, availability, "X people viewing" — real or absent. Never generated, never estimated, never defaulted to a plausible number. Fake structured data risks a Google manual action and would end the app.

## B4. Zero theme injection by default
No writes to `theme.liquid` or any theme file in v1. Storefront output goes through the theme app extension app embed only. If `write_themes` is granted later, back up the original file content before any write and restore it on uninstall.

## B5. Metafields survive uninstall
On `app/uninstalled`, restore theme backups but **leave SEO metafields in place**. They are the merchant's content. Deleting them is precisely the behaviour generating 1-star reviews for competitors.

## B6. Zero storefront JS
The app embed emits `<script type="application/ld+json">` and nothing else. No runtime JavaScript, no CSS, no fonts, no tracking. Our entire positioning depends on this.

## B7. No script tags
`scriptTagCreate` / `scriptTagUpdate` break on 1 Oct 2026 and stop running entirely on 1 Mar 2027, across all API versions. Never use them.

## B8. GraphQL only
REST Admin API is legacy for new public apps. No REST calls anywhere, including the Asset resource.

## B9. Minimum scopes
Exactly the four required scopes at install. Everything else via `optional_scopes` requested at feature-enable time. Never request customer, order, draft-order or `read_reports` scopes.

## B10. Bulk operations for large catalogs
Anything touching the whole catalog uses `bulkOperationRunQuery` / `bulkOperationRunMutation`. A 5,000-product store must not silently fail on rate limits.

## B11. Honest limitations in the UI
Where the platform blocks us, say so in the interface: sitemap is not editable, canonical cannot be removed, URL structure is fixed, `llms.txt` is unproven. Merchants churn from broken promises, not from honest constraints.

## B12. No keyword density
Nowhere in scoring, suggestions or copy. Scoring is based on intent match, data completeness and real GSC performance.

## B13. Compliance is Phase 0
GDPR webhooks, `app/uninstalled`, Billing API, session tokens, Polaris. Built at the start, never bolted on before submission.

# PART C — CODE CRAFT

- Every feature ships with its error states designed, not just its happy path.
- Every queue job is idempotent.
- No hardcoded shop domains, tokens, or test data in application code.
- Admin UI uses Polaris components, not custom CSS reimplementations.
- Log enough to debug a merchant issue without asking them for screenshots.
- If it would embarrass us in an App Store review, it is not done.
